# noyalib v0.0.28 Release Notes

The **implicit null** cut. Two correctness fixes in the CST and the
scanner, both about a mapping entry whose value is absent: one could
not be written to, and the other was not recognised when the document
ended on the colon.

No public API change. No MSRV change (still 1.86.0). Both fixes are
behavioural, so a consumer on 0.0.27 sees different — correct — values
for the documents described below.

## Highlights

### Inserting over an implicit null no longer duplicates the key

Reported as #310, fixed in #311.

Given `a:`, inserting a value for `a` emitted a *second* `a` entry
instead of filling the empty one.

What made this hard to catch is that the load-back oracle could not see
it. The loader resolves duplicate keys last-wins, so the emitted
document loaded back as the pre-edit value with the insertion applied —
exactly what a round-trip test asserts. The duplication existed only in
the bytes.

It also relocated the entry to the end of the mapping, and where the
entry carried a trailing comment, that comment was left attached to the
key it had just shadowed.

### A `:` at end of input is a value indicator

Reported as #312, fixed in #313.

`a:` and `a:\n` are the same document one byte apart — a trailing
newline is not content — and the library disagreed with itself about
them:

| Input | Before | After | PyYAML / Psych |
|---|---|---|---|
| `"a:"` | `String("a:")` | `{a: null}` | `{a: null}` |
| `"a: 1\nb:"` | **parse error** | `{a: 1, b: null}` | `{a: 1, b: null}` |
| `"p:\n  a:"` | `{p: String("a:")}` | `{p: {a: null}}` | `{p: {a: null}}` |
| `"- a:"` | `[String("a:")]` | `[{a: null}]` | `[{a: null}]` |

The second row is the one most likely to be hit in practice: it needs
only an ordinary mapping with a blank last value and no trailing
newline. `printf` without `\n`, heredocs, editors configured not to add
a final newline, and generated fragments all produce such files. It
failed with `simple key was required but not found` — a hard error on
valid YAML that two reference implementations accept.

The other three were silent wrong values, which is worse per
occurrence: a consumer reading `p.a` got nothing and had no way to
notice.

#### Cause

The plain-scalar scanner decides whether a colon ends the scalar by
looking at the byte after it. With nothing after it, both sites
substituted a NUL:

```rust
let next = if len + 1 < remaining.len() { remaining[len + 1] } else { 0 };
if Self::is_blank_or_break(next) { break; }
```

`IS_BLANK_OR_BREAK[0]` is `false`, so the test failed and the scalar
swallowed the colon.

The rule was already known elsewhere in the same scanner — the token
dispatcher has `b':' if next_is_terminator`, and the trailing-whitespace
predicate twelve lines below the first broken site spells it
`j + 1 >= remaining.len() || is_blank_or_break(...)`. Only these two
sites failed to apply it.

## Compatibility

- **API:** unchanged.
- **MSRV:** unchanged at 1.86.0.
- **Behaviour:** documents matching the shapes above now load as
  mappings rather than scalars, and one previously-failing document now
  parses. Code that relied on `"a:"` loading as the string `"a:"` was
  relying on a bug that PyYAML and Psych do not share.

## Verification

- Nine regression tests for the scanner fix, each observed failing
  before the change.
- Full suite 5754 passing, including the strict YAML conformance suite.
- Miri (focused) green on the scanner change — the fix moves a bounds
  condition in a SIMD-routed hot path, which is precisely where an
  off-by-one would hide.
