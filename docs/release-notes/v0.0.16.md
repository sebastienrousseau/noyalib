# noyalib v0.0.16 Release Notes

A **build-fix, MSRV, and dependency-refresh** cut. `main` had been left
unbuildable under `cargo check --all-targets` on default features by a
feature-gated import; that is fixed. Alongside it, the minimum supported
Rust version moves to **1.86.0** for the whole lockstep set, the MSRV
bump policy is rewritten to match the project's actual `0.0.x` posture,
and the optional `jsonschema` dependency moves 0.46 → 0.48.

No public API additions, removals, or signature changes
(`cargo-semver-checks` green). Two deserialiser **error messages** change
wording — see *Behavioural changes* below.

## Why this release exists

Three unrelated pressures converged:

1. **`main` did not build under `--all-targets`.**
   `tests/coverage_value_serde.rs` imported `to_value` unconditionally
   while its only consumer sat behind `#[cfg(feature = "lossless-u64")]`.
   With default features the import was unused, and `-D unused` promoted
   that to a hard error. Anyone running `cargo check --all-targets` on a
   fresh clone hit it.
2. **The documented MSRV had drifted from reality.** Several documents
   still claimed a 1.75 core floor with satellites at 1.85, while
   `rust-version` had said 1.85 since v0.0.5, and `src/lib.rs` stated a
   third, different bump policy again. Three sources of truth, none
   agreeing.
3. **The dependency set had aged**, with `jsonschema` two minor versions
   behind and a batch of Dependabot action bumps outstanding.

## What changed

### Fixed

- **`cargo check --all-targets` builds again on default features.** The
  `to_value` import is now gated by the same `cfg` as its consumer
  rather than deleted — deleting it would have compiled by default while
  breaking every `--all-features` build.

### Behavioural changes (error messages only)

Error *message* wording is explicitly outside the stability contract
(variant names are stable); both changes make previously-useless text
actionable. No `Error` variant, `kind()` classification, or miette code
changed.

- Deserialising a `Number::Unsigned` above `i64::MAX` into an `i64`
  previously produced **`type mismatch: expected integer, found
  integer`** — `type_name` collapses `Integer` and `Unsigned` onto the
  same label, so both sides of the mismatch rendered identically. It now
  reads `type mismatch: expected signed integer (i64), found unsigned
  integer 18446744073709551615, above i64::MAX`. Requires
  `lossless-u64`.
- The mirror case — a negative `Number::Integer` deserialised into a
  `u64` — previously said `found integer` without mentioning the sign.
  It now reads `type mismatch: expected unsigned integer, found negative
  integer -1`.

### Changed — MSRV 1.85 → 1.86

- **The minimum supported Rust version is now 1.86.0**, for the core
  library and every satellite alike. 1.86 is the lowest toolchain the
  project can be **built and tested** on. Verified directly, with
  `rust-version` temporarily set to 1.85:

  | Command on `rustc 1.85.0` | Result |
  |---|---|
  | `cargo check --lib --locked` | compiles cleanly |
  | `cargo check --all-targets --locked` | **fails** — `criterion@0.8.2 requires rustc 1.86` |

  `criterion 0.8` is a dev-dependency, so it does not constrain
  *downstream consumers* — but it does mean no test run, bench, or
  coverage job can execute on 1.85. Publishing 1.85 would therefore be
  an MSRV the project has no way to verify, and nothing would catch the
  day it silently broke. **We publish the floor we test.** If you are
  pinned to 1.85 and cannot move, **v0.0.15 remains available and this
  is the only reason to stay on it.**
- **The bump policy is now explicit: never speculative.** The MSRV moves
  only when the toolchain we build and test at actually moves — never
  for tidiness or "headroom", since an MSRV can always be raised the day
  it is needed and raising it early only costs downstream users. As a
  standing guarantee, noyalib will not require a rustc newer than
  **12 months old** at release time; 1.86.0 shipped 2025-04-03.
- **The historical split MSRV is gone.** The whole lockstep set now
  shares one floor, recorded in `docs/POLICIES.md` §1, which is the
  single source of truth.
- **The MSRV CI job was renamed `msrv-1-85-core` → `msrv-core`** so
  future bumps do not churn the job name. **Action required for
  maintainers:** if `msrv-1-85-core` is a required status check in
  branch protection, update the rule to `msrv-core`, or PRs will block
  on a check that no longer reports.
- `shared-msrv-core.yml`'s default `toolchain` input moved to `1.86.0`.
  Satellites calling it *without* an explicit `toolchain:` adopt 1.86
  when they next bump their pinned SHA.

### Changed — MSRV bump policy

- **On `0.0.x`, an MSRV bump ships as a patch, not a minor-version
  event.** `docs/POLICIES.md` previously called a core MSRV bump a
  minor-version event; taken literally this release would have had to be
  `0.1.0`. But §2 of the same document commits to iterating
  `0.0.2 … 0.0.99` first, so there is no minor slot to spend — the two
  rules contradicted each other. Cargo treats every `0.0.x` as its own
  incompatible version anyway.
- MSRV bumps must now be called out under an explicit
  `### Changed — MSRV` heading in `CHANGELOG.md`, as here.
- **This reverts to a genuine minor-version event at `1.0`**, per the
  gates in `PLAN.md`. The superseded rule is quoted in full in
  `docs/POLICIES.md` rather than deleted.

### Changed — dependencies

- **`jsonschema` 0.46 → 0.48**, optional, behind `validate-schema`. The
  consumed surface (`validator_for`, `JsonType`,
  `error::{TypeKind, ValidationErrorKind}`) is unchanged. No behavioural
  delta: the 55 tests across `schema_validate`, `schema_codegen`,
  `coverage_schema_validate`, `coerce_to_schema`, `coerce_to_schema_extra`
  and `cst_schema_tag_audit` pass unmodified against 0.48.
- Three new transitive crates arrive with it, reachable only under
  `validate-schema`: `jsonschema-value`, `strum`, and `strum_macros` (a
  proc-macro). Each is a version-pinned `safe-to-deploy` exemption in
  `supply-chain/config.toml` pending upstream audit; all clear the
  `cargo-deny` licence allowlist.
- **The lockfile is otherwise unchanged from v0.0.15.** An earlier
  revision of the release branch refreshed 71 crates; it was reverted
  before merge because `cargo-vet` exemptions are version-pinned and the
  refresh invalidated 81 of them at once, which would have meant adding
  81 unaudited exemptions to keep a deliberate gate green. The shipped
  lockfile is the v0.0.15 baseline plus the `jsonschema` bump — a
  six-crate vet surface a reviewer can actually check.
- Pinned action SHAs refreshed across every workflow
  (`dtolnay/rust-toolchain`, `github/codeql-action` v3 → v4.37.1,
  `EmbarkStudios/cargo-deny-action` v2.0.20 → v2.1.1); the
  `Dockerfile.full` builder image moved `rust:1.96-bookworm` →
  `rust:1.97-bookworm`, digest-pinned as before.

### Documentation

- **Corrected a `no_std` instruction that tested nothing.**
  `docs/POLICIES.md` previously recommended
  `--no-default-features --features minimal` for `no_std` verification.
  But `minimal = ["std"]` — it is a *dependency-budget* alias that turns
  `std` back on while dropping `itoa`, `ryu` and `serde_ignored`. That
  command silently produced a `std` build. The correct invocation is
  `--no-default-features` alone, which is what CI has always run.
- **Scoped the `no_std` claim to hosted targets.** "no_std" here means
  alloc-only on a hosted target (native host + `wasm32-unknown-unknown`).
  Bare-metal `*-none` targets do **not** build today: `indexmap`,
  `rustc-hash` and `memchr` are declared without
  `default-features = false`, and the crate uses `rustc_hash::FxHashMap`,
  which needs `std`. Both blockers are pre-existing and now documented as
  a deliberate non-goal rather than an oversight. Open an issue if you
  need it.
- MSRV statements synchronised across `README.md`, `src/lib.rs`,
  `CONTRIBUTING.md`, `GLOSSARY.md`, `GOVERNANCE.md`, `SUPPORT.md`,
  `MIGRATION.md`, `GETTING_STARTED.md`, `docs/POLICIES.md`,
  `docs/BENCHMARKS.md`, `docs/PGO.md` and
  `docs/diagrams/dependency-graph.md`.
- Added `examples/strict_deserialise.rs` — the `strict-deserialise`
  feature had no example despite being default-on. It demonstrates the
  silent-typo failure mode (`porrt: 9090` accepted by plain `from_str`),
  the same document rejected by `from_str_strict`, nested detection,
  `from_slice_strict`, and that strictness is per call site.

### Testing (no behavioural change)

- New coverage for public API that had **zero** test references —
  `Mapping::get_index_of`, `cst::Document::comments_at`, `schema_for`,
  `schema_for_yaml` — found by cross-referencing every `pub fn` in
  `src/` against the whole `tests/` tree.
- New coverage for the `lossless-u64` `Number::Unsigned` widening and
  overflow-rejection arms, and for the `cst::format` flow-collection
  paths. Exercising the overflow arm is what surfaced the
  `expected integer, found integer` defect fixed above.
- `interpolate_properties_redacted` had no coverage at all while its
  strict and lossy siblings were well covered; it now has four tests,
  including the negative assertion that is the whole point of the API
  (the placeholder name must not leak into the error) and one
  documenting that interpolation applies in place as it walks, so a
  mid-walk failure leaves earlier entries substituted.

## What did not change

- Public API surface — no additions, removals, or signature changes.
- Parse and serialise behaviour for well-formed input — identical.
- `#![forbid(unsafe_code)]` — intact across the workspace.
- No new *unconditional* runtime dependencies; the three new transitives
  are reachable only under the optional `validate-schema` feature.

## Upgrading

For most users this is a drop-in patch bump:

```toml
[dependencies]
noyalib = "0.0.16"
```

Two things to check:

1. **You are on Rust 1.85.** You must move to 1.86.0 or stay on
   v0.0.15. This is the only reason to stay.
2. **You match on deserialiser error text.** Two `TypeMismatch` messages
   changed wording (see *Behavioural changes*). Match on
   `Error::TypeMismatch { .. }` or `Error::kind()` instead of the
   rendered string — the variant and classifier are stable, the wording
   is not.

## Follow-ups noted for v0.0.17

- Still open from v0.0.14: migrate `max_sequence_length` /
  `max_mapping_keys` from `Error::Serialize("… limit exceeded")` to
  `Error::Budget(BudgetBreach::…)` for full `Error::kind()` classifier
  parity.
- The `serde` group (#201) and `tokio-stack` group (#202) Dependabot PRs
  were closed rather than merged when the lockfile refresh was authored;
  those updates are **not** in this release and will be re-proposed
  against the next published version, each with its own reviewable
  `cargo-vet` delta.
- `validate-schema` compiles on the MSRV toolchain but is **not** gated
  there — `shared-msrv-core.yml` runs only no-default-features, default,
  and clippy. Adding an optional-feature leg to the MSRV gate would close
  the gap between what is verified by hand and what CI enforces.
- No CI gate asserts that a tagged release carries a matching
  `docs/release-notes/vX.Y.Z.md`, though `docs/CII-BEST-PRACTICES.md` claims
  one exists per release. This file was initially missed for that reason.
